Why UDB exists

One policy-aware contract in front of every backend

Most growing products end up with user data in Postgres, search in Elasticsearch, embeddings in a vector store, files in object storage, cache in Redis, analytics in ClickHouse — and the same security headers, retry rules, schema versions, RLS policies, and audit trails re-implemented in every service. UDB puts that contract in one place: describe your domain in normal .proto files, annotate where data lives, and run one broker. Your app sends “select invoices”, “upsert this customer”, “search these vectors”, or “can this user read this resource?” — the broker checks the request, resolves the active catalog, talks to the right backend, and returns a typed response.

Built for production

Capabilities that ship in the box

🗄️

Every backend, one typed API

Relational, vector, object, cache, document, graph, time-series, and analytical operations across 18 backend kinds — compiled to a neutral IR, then to the backend dialect.

🔒

Multi-tenant isolation

Per-tenant RLS, field-level AES-256-GCM-SIV encryption, and CDC/backup/replication scope guards — fail-closed everywhere a request crosses a tenant boundary.

🔁

Transactions & sagas

Per-request transactionality, real Postgres 2PC / MySQL XA, and sagas with lease-protected recovery.

📡

CDC → Kafka

Transactional outbox with DLQ, topic policy, durable delivery proof, and exactly-once mode.

🪪

Native auth & identity

JWT/MFA/sessions, RBAC+ABAC+ReBAC over Casbin, and OIDC/SAML/SCIM federation.

🧱

Proto-driven migrations

Staged/activate/rollback catalogs and migration plan/apply with review gates and an audited op ledger — security annotation changes surface as visible drift items.

📊

Observability & SLOs

Prometheus metrics, OpenTelemetry spans with trace propagation, defined SLOs/error budgets, gRPC health per listener, and edge backpressure.

Same contract, every language

Describe the model, call one API

invoice.proto
message Invoice {
  option (udb.core.common.v1.pg_table) = {
    table: "invoices"  schema: "billing"
  };
  string invoice_id  = 1 [(...pg_column) = { primary_key: true }];
  string tenant_id   = 2 [(...pg_column) = { tenant_column: true }];
  string customer_id = 3;
  int64  total_cents = 4;
}
from udb_client import Metadata, UdbClient

meta = Metadata(tenant_id="acme", project_id="billing",
                scopes=("udb:read",))
with UdbClient("127.0.0.1:50051", meta) as udb:
    rows = udb.select(message_type="acme.billing.v1.Invoice",
                      limit=50)
    print(rows)
import udb "github.com/fahara02/udb/sdk/go/udbclient"

u, _ := udb.NewUdb(ctx, udb.Config{
    Target:   "127.0.0.1:50051",
    TenantID: "acme", ProjectID: "billing",
})
rows, _ := u.Data.Select(ctx, "acme.billing.v1.Invoice", 50)
import { createUdb } from "@udb/sdk";

const udb = createUdb({ target: "127.0.0.1:50051",
                       tenantId: "acme", projectId: "billing" });
const rows = await udb.data.select({
  message_type: "acme.billing.v1.Invoice", limit: 50 });

Interactive · runs in your browser

Not just docs — UDB itself, in WebAssembly

UDB's real proto parser (the udb-portable crate compiled to WASM) runs entirely client-side. Paste a UDB-annotated .proto and watch UDB produce the exact catalog schema — tables, columns, RLS, per-column data classes — and the same deterministic manifest checksum the server computes.
